current size for nearly every path, meaning code was written once and kept rather

### Confirmed defects — the reach of the gate

**G-1 — `npm run build` succeeds on a `career.json` that `npm run validate`
rejects.** The `gate` path (`src/derive/index.ts:396` `checkArtifact`) reads the
committed artifact and the import boundaries, and never calls `validateCareer`.
`validateCareer` is invoked only from `runPipeline` (`index.ts:118-124`), which is
the `solve` path. `build` is `npm run gate && vite build` (`package.json:11`) and
never runs `solve` — by design (AD-1).

Reproduced on a full copy of the tree with `node_modules` linked: with
`career.json` carrying both an unknown key (`notabel`) and a `null` in the
required `duration`, `node src/derive/index.ts --check` printed "the layout
artifact is present and valid." and exited **0**, while `node src/data/validate.ts`
on the same file exited **1** naming both faults. The AC 1.2 promise — "the build
**fails**... a non-zero exit code, not a warning" — is held by a script nothing on
the build path runs. *Disposition: fix.*

**G-2 — The same gap lets committed data and committed artifact drift silently.**
On the same copied tree, with `career.json` extended to two Clients while
`generated/layout.generated.json` still described one, the gate passed clean and
exited 0. `npm run build` would ship a site silently missing an entire Client the
author had added. This limitation is *documented*
(`src/derive/README.md:198`: the gate "counts from the artifact's `clients` tree,
**never from a fresh derive**... `npm test` is what catches it") and a real test
closes it — `src/derive/artifact.test.ts:465`, "the committed artifact matches
what the pipeline produces now". *Disposition: fix — see G-3, which is why that
test does not help.*

**G-3 — Nothing runs `npm test`. There is no CI, no git hook, and no npm
lifecycle hook.** Verified: no `.github/workflows/`, no `.gitlab-ci.yml`, no
`.circleci`, no `azure-pipelines.yml`, no `.husky`, no non-sample hook in
`.git/hooks/`, and the only lifecycle script in `package.json` is `preview`.

This is the highest-leverage finding of the epic, because it is what turns three
otherwise-closed gaps into live ones. The 358-test suite holds the drift guard
(G-2), the determinism regression test (AC 1.4), the NFR-5 maintenance contract,
the NFR-6 network ratchet, and every mutation guard the story-1.5/1.6/1.7 review
loops added — and all of it runs only when a human remembers to type `npm test`.
`build` runs `gate` and `vite build`; neither runs a test.
*Disposition: fix — this is the top action item.*

#### The gate certifies self-contradictory artifacts

**L-1 — A `clientId` naming no Client passes the gate.** Reproduced: editing the
committed artifact so `clients[0].projects[0].clientId` reads
`client:not-a-real-client` while the Project still sits inside `client:sncf` yields
"the layout artifact is present and valid.", exit **0**. `clientId`
(`artifact-schema.ts:83`, emitted at `artifact.ts:44`) is the Project's back-reference
to its owner, and nothing confirms it points at its actual parent — though
`checkDestinations` already walks every client/project pair and could test it in one
line. A consumer resolving ownership by `clientId` and one reading the tree get
different answers: the two-consumers-disagree divergence AD-14 exists to prevent,
reproduced *inside a single document*. *Disposition: fix.*

**L-2 — `isDeep` may contradict the `notable` it derives from.** Reproduced:
flipping `isDeep` to `false` on a Project whose `content.notable` carries 671
characters of prose passes the gate clean, exit **0**, and the Client's Dwell tempo
still reads `dwell-steady` — the tempo the *Deep* count produced. The artifact
carries both the derived flag and the authored field it derives from, and nothing
re-asserts the one derivation it holds both halves of. Story 1.3's central promise —
"no two consumers can disagree about the entry's class" — is unenforced at the one
boundary where two consumers actually meet. Checking it needs no re-derive and no
re-solve, so it stays inside AD-1. *Disposition: fix.*

**L-3 — The artifact's `asOf` may drift from the authored `asOf`, and the
consequence is severe.** Reproduced twice.

First, drift is undetected: rewriting the committed artifact's `asOf` to `2020-01`
while `career.json` still says `2026-09` passes the gate, exit **0**.

Second, and worse, the *authored* `asOf` is unbounded against the data it measures.
On a three-Client fixture spanning 2019–2024, `asOf: 2026-09` derives a correct
spread — `stroke-dust`/`stroke-rest`/`stroke-near` at `timeAxis` 0/0.5/1. Changing
only `asOf` to `2018-01` (earlier than every entry) makes all three Clients
`stroke-near`, `timeAxis: 1`, `mass: 4`. **Two of the three mapping rules collapse to
a constant**, the Fallback's whole timeline stacks at one point, and `solve` exits
**0** with a schema-valid artifact.

`asOf` is the single input every span and every recency is measured against
(`schema.ts:114-129`), so it is the one field whose drift invalidates every derived
number at once. `AUTHORING_HORIZON` bounds `duration.end` but nothing bounds the
reference month `end` is compared *against*. This is FR-3's entire visual derivation
degrading silently while every check reports success.
*Disposition: fix — a `CareerSchema` refinement rejecting an `asOf` that precedes any
`duration.start`, plus a `sourceDigest` in the artifact so the gate can detect drift
without re-deriving.*

#### The emitter and the gate check different things

**L-4 — `solve` writes an artifact from a tree the `gate` would reject.**
Reproduced: with an AD-3 violation planted at `src/render-scene/probe.ts`,
`node src/derive/index.ts` (solve) exits **0** and writes the artifact, while
`node src/derive/index.ts --check` (gate) on the identical tree exits **1**.
`checkArtifact` runs four checks — schema, destinations, stops, and
`checkImportBoundaries` (`index.ts:505`) — while the pre-write `checkEmittedArtifact`
(`index.ts:88-105`) runs only the first three; story 1.8 added the boundary check to
the gate path alone. The failure therefore arrives attached to the wrong action, at
the wrong moment. `checkEmittedArtifact`'s own header claims to hold "every check an
assembled artifact must pass before its bytes are written" and enumerates "three of
them" — a doc comment that states its own completeness and is now wrong.
*Disposition: fix — call `checkImportBoundaries` from the emitter too, or correct the
header to state the asymmetry.*

#### Boundary-parser holes (independent of the table gaps at B-2 through B-5)

**L-5 — Three import forms escape the walker silently.** The adversarial and
edge-case lenses agreed here, each verifying independently: `require('../data/schema.ts')`,
`createRequire(import.meta.url)('../data/schema.ts')`, and a dynamic import through a
variable (`const p = '../data/schema.ts'; await import(p)`) all return no findings
from `findImports` (`boundaries.ts:440-491`). Meanwhile `src/data/README.md:6` states
the ban absolutely: "A dynamic `import(...)` does not escape it."

Both lenses noted the parser is otherwise strong — `export * from`, side-effect
imports, template-literal dynamic imports, import attributes, and comment/string
decoys are all handled correctly. The remaining holes are narrow, but they fail
*silently*, which `boundaries.ts` itself (`:13-19`, `:598`) calls worse than having no
gate. A `createRequire` shim for reading JSON in an ESM file is a normal reflex, not
an attack. *Disposition: fix — reject what cannot be resolved rather than passing it,
and narrow the README's absolute claim to literal specifiers.*

#### Schema permissiveness

**L-6 — Four unconstrained arrays let an empty artifact certify as correct.**
`clients`, `destinations`, `dwell` and `shots` (`artifact-schema.ts:184,191,196,201`)
carry no `.min(1)`, and neither does `CareerSchema.projects` (`schema.ts:132`).
Confirmed end to end earlier in this retro: `projects: []` validates, solves, emits
`clients: 0, destinations: 0, dwell: 0, shots: 0`, and **passes the gate**. Note
`ArtifactClientSchema.projects` *does* carry `.min(1)` at `:167`, so this is the same
guard simply not applied one level up. *Disposition: fix.*

**L-7 — Two distinct Clients whose names share a slug merge silently.**
Reproduced: `Acme Corp` and `Acme-Corp` as two separate authored entries derive one
Client (`client:acme-corp`, name `Acme Corp`, both Projects, 3 destinations), and the
second spelling disappears. `deriveEntities` guards duplicate *Project* IDs
(`entities.ts:212-224`) but never duplicate *Client* IDs.

This one needs care, because the folding is **deliberate and documented**:
`src/derive/README.md:112` argues that divergent spellings of one client are a
data-entry reality and that emitting two Stars for one organisation is the worse
failure. That reasoning is sound. The gap is not the folding but the *silence* —
nothing distinguishes "two spellings of one client" from "two clients I meant to keep
apart", and in the second case NFR-5's promise fails invisibly: the entry is added,
validates, solves, and is simply not there. *Disposition: fix — warn (or require an
explicit alias declaration) when the folded spellings differ, rather than removing the
fold.*

#### Coverage

**L-8 — The NFR-5 maintenance contract is verified only for the cheapest entry.**
`maintenance.test.ts:117` hardcodes `client: 'SNCF'` — the Client already in
`career.json` — and `:250`'s promotion fixture builds a single Client. So "adding an
entry costs one object plus one number" is proven only for a Project joining an
*existing* Client. Adding the first genuinely new Client is the common case as the
file grows toward ~16 entries, and it is the path that exercises Rail spacing,
`forceLink`/`forceManyBody` relaxation, and `assertOrbitOwnership` — whose inner loop
(`solve.ts:521-534`) needs a second Client and so performs **no check at all** on
today's committed single-Client data. *Disposition: fix — a maintenance case that
appends a new Client and asserts the Client-granular consequences.*

**L-9 — The Shot-containment guard re-implements the rule it guards.**
`widestOrbitOf` (`shots.ts:117-123`) is transcribed a third time inline in
`checkStops` (`index.ts:296-298`). `shots.ts:107-113` argues the *solver's* copy
(`solve.ts:243-249`) is deliberate — Rail spacing is a different question from
framing — and that reasoning holds. It does not extend to the third copy, which
exists purely to re-check `shots.ts`'s output, so the guard and the thing it guards
now compute their shared premise separately. Both `FRAMING_MARGIN` and
`MIN_SHOT_DISTANCE` are documented as provisional and greybox-tunable, which is
exactly when the two walks would diverge. *Disposition: fix.*

**L-10 — The gate's success message names no file.** `main()` (`index.ts:555`) reads
`argv.find((arg) => arg !== '--check') ?? ARTIFACT_PATH`, a documented test seam, so
`npm run gate -- some/other.json` validates a substituted path and prints the
unconditional "the layout artifact is present and valid." The equivalent seam in
`validate.ts` carries a comment noting nothing documents it; this one does not.
Observed directly in this retro: every scratch-copy gate run printed a success line
that could not be told apart from one about the committed artifact. *Disposition: fix
— name the path in the message.*

#### Edge-case lens: unhandled paths at the story seams

Reported by the edge-case lens and consistent with everything verified above. Those
already confirmed by direct reproduction are cross-referenced rather than repeated:
empty `projects` (L-6), the Client slug collision (L-7), `asOf` unbounded (L-3),
`src/types/` ungoverned (B-4), the parser holes (L-5). The remainder, reported with
`file:line` and reproduction but **not** independently re-verified in this retro:

- **Coincident Bodies pass the gate.** `assertOrbitOwnership` runs inside `solveLayout` only, never at gate time (correctly, under AD-1), so an artifact carrying two Bodies at identical coordinates is accepted (`index.ts:271-380`, `solve.ts:501-536`).
- **A Client owning no Projects passes the gate.** The solve guards it; the gate does not (`index.ts:200-203`, `:285-305`).
- **Orbit angles wrap past 2*PI at 19 or more Projects on one Client** (`solve.ts:463-471`), landing two Projects about 0.017 rad apart. Not reachable at the current inventory.

*Disposition: defer as a group — each is a gate-side re-assertion of an invariant the
solve already holds, and none is reachable from today's committed data. They belong
with L-1/L-2 in one "gate content checks" work item.*

### Narrowed scope

This is consistent with L-8 (single-Client fixtures throughout) and with the
observation that AC 1.4 only requires two solves *in one process* — but it was not
carried to a verified conclusion, and it is recorded as unverified. A dedicated

Consequence for this retro: the third lens's coverage — regression gaps,
missing-adoption gaps, and broken-verification gaps across the epic diff — is

as an absence of verification gaps.

### Process lessons

- **A story can be marked `done` with a declared AC group knowingly unimplemented.** S-2 is the case: story 1.8's bundle assertion was deferred deliberately and recorded honestly in `deferred-work.md`, but `sprint-status.yaml` says `done` and nothing reconciles the two. *Lesson: when a story ships with a declared AC unmet, the deferral belongs in the status file — a `done-with-deferrals` marker, or an action item opened at the moment of deferral — not only in a side document a later reader may not open.*
- **The review loop worked, and its cost is visible.** Iterations climb across the epic: 1.1-1.3 at 1, 1.4 at 0, 1.5 at 3, 1.6 at 2, 1.7 at 1, 1.8 at 4. The three fix commits (`6f2e6ae`, `fdc8d1c`, `610144c`) each reproduced every finding by mutation before acting, and explicitly dismissed false subagent claims — `6f2e6ae` records "six subagent claims were dismissed as false or overstated". *Lesson: keep this. It is the practice that makes the codebase's own claims trustworthy, and it is why this retrospective could verify so much so quickly.*
- **`deferred-work.md` is functioning as a running retrospective, and it is unusually good** — source-referenced, mutation-verified, re-verified against the tree on 2026-09-06, and honest enough to record a claim that turned out **false** on re-check (the interpolated dynamic-import escape, `deferred-work.md:395-399`). *Lesson: keep it, and give it a route into `sprint-status.yaml`'s `action_items` so items are tracked where the sprint tooling can see them.*
- **Commit subjects name no story ID.** `git_evidence.py` returned `stories: []` for all 12 commits, so machine attribution was impossible and the story-to-commit table in this document is inferred from sequence, dates, touched paths and each spec's `baseline_commit`. *Lesson: put the story id in the commit subject or trailer — it costs nothing at write time and it is the difference between a scripted evidence pass and a manual one.*
- **Session logs did not exist for any story.** Process-lesson analysis was therefore limited to what commits and documents reveal; the reasoning behind abandoned approaches is not recoverable. The one stash (`729142a`, "story-1-5 iteration-1 implementation (bad_spec loopback)") is the only surviving trace of a discarded attempt. *Lesson: if the why matters later, it has to be written down somewhere durable at the time.*

## Acceptance verdict

**Verdict: accepted-with-open-items.** Criteria were **declared** (epic spec,

### Why not "rejected"

`pending_stories` is **empty** — all 8 stories are `done` in `sprint-status.yaml`, so
the rule that forces a machine **rejected** does not apply. No blocking finding
stands: the epic's central structural promises hold under direct test. AD-3's single
read path is real in the code and enforced by a gate that fires with precise
diagnostics; the solve is deterministic across a process boundary, not merely
in-process; the artifact contract is versioned, banner-guarded, LF-pinned and
committed; `solve` is genuinely separate from `build`; the destination set is single,
content-addressed and cardinality-checked; Dwell and Shots are Client-granular with no
world coordinates. `npm test` is 358/358, `typecheck`, `gate` and `build` all exit 0.
Test-to-production ratio is 1.98:1 and no god-class emerged.

### Why not "accepted"

Two things stand open that the criteria themselves named.

**One declared AC group was not implemented.** Story 1.8's AC group 2 — the CI bundle
assertion over bundler output, with an entry-chunk reachability ban and a size
budget — does not exist in any form. The story is nonetheless `done`. It was deferred
deliberately and documented well (`deferred-work.md:89-103`), which is why this is an
open item rather than a rejection; but a declared criterion is unmet, and the status
file does not say so.

**Several declared guarantees are held by prose or by a suite nothing runs.** AC 1.2's
"the build fails... non-zero exit code" is held by `npm run validate`, which the build
path never invokes (G-1). The data/artifact drift guard exists as a real test
(`artifact.test.ts:465`) but no CI, git hook or lifecycle hook runs it (G-2, G-3).
`src/shell/README.md:3`'s "no Three on the entry path" is enforced by nothing (B-2).
`src/data/README.md:6`'s absolute claim that dynamic imports cannot escape the ban is
false for three import forms (L-5). And a stale `asOf` collapses two of the three
mapping rules to constants with every check reporting success (L-3).

None of these is a defect in what was built. Each is a gap between what the documents
claim and what the tooling enforces — which is precisely the failure mode this epic
was written to eliminate, and precisely what action items 1-3 close.
