# src/shell/

Entry, capability detection, routing, navigation state machine, and the persistent DOM destination index. `entry.ts` carries no React and no Three — it detects and dynamically imports, so the entry path never statically reaches Three, the solver, or the raw career JSON (AD-7; see the root README's Reference section).

**Imports:** `generated/layout.generated.json` and `src/tokens/` statically; `src/render-scene/`, `src/render-fallback/` and `src/colophon/` through dynamic import only. Never `src/data/`, never `src/derive/`, and never `three`, `@react-three/fiber`, `@react-three/drei` or the solver's `d3-force-3d` by package name.
**Imported by:** the app entry point. Renderers are reached only through dynamic import from here.

## The index reads, and never derives

Every ordering rule the index obeys was resolved in `src/derive/` and emitted into the artifact (AD-3). The Rail's sequence arrives as `rail`, each Client's Projects arrive already ID-ordered inside `clients[]`, and Deep/Shallow arrives as `isDeep`. Nothing in this directory sorts on a `duration`, a `timeAxis`, or a coordinate, and a source scan in `index-model.test.ts` fails if it starts to.

That matters because the Rail's ordering is not the artifact's `clients` ordering: `clients[]` is `timeAxis` order (max recency), and the Rail sorts on earliest `duration.start`. For a portfolio holding a long early engagement beside a short late one the two genuinely differ, so an index reconstructing the Rail from the tree would walk a different sequence from the one the camera travels — and it would put the Rail's sort key in a second place, where the two copies drift.

**Index order is Rail order reversed: present → past.** The artifact emits `rail` oldest-engagement-first, because that is the direction the camera travels; a reader arriving at a portfolio wants the current work first. It is the same ordering read the other way, not a second one.

## Why the model and the renderer are separate files

`node --test` under Node 24's built-in type stripping cannot load a `.tsx` file **in any position** — `ERR_UNKNOWN_FILE_EXTENSION` at module resolution, before any transform, so a `.ts` test cannot even import a `.tsx` module. Adding a transform means adding dependencies to a set that is deliberately closed at fifteen exactly-pinned versions, in a repo that rejected ESLint on exactly that ground.

So every rule an acceptance criterion names lives in `index-model.ts`, which is pure `.ts` and testable with zero new dependencies, and `index-nav.tsx` is a mapping thin enough that reading it is sufficient verification. The residual risk — that the JSX mapping itself is unasserted — is accepted and ratcheted: `index-model.test.ts` scans the renderer's source and fails if it grows a sort, a filter, a hook, a re-derivation, or a reach into render state.

## Deep and Shallow are text, never an attribute

A screen-reader user must be able to answer *which of these is worth reading* from the index alone. An `aria-*` attribute does not answer it, and a dot or a colour answers it for nobody who cannot see. So the state is rendered as the words `Deep` and `Shallow` inside the entry, where they land in its accessible name. The vocabulary is load-bearing and pinned by test: no synonyms.

## The page and the index under the keyboard (3.9)

The page is one full-bleed void: `page.css` sets the ground to `surface-base` edge to edge, stops the document scrolling, and fixes the scene host to the viewport, so the canvas (`100%` by `100%`) fills the frame. The first frame shows the identity line top-left, the instruction bottom-right, and nothing else of the DOM.

The index is still the interface (AD-4) and still first in document order, but it is not drawn at rest. Each entry is clipped to nothing — out of sight and out of the pointer's reach, in the accessibility tree and the tab order. Tab reveals exactly one entry, the one holding `:focus-visible`, bottom-left, in the chrome's type and ink; a mouse focus (`:focus` without `:focus-visible`) reveals nothing. A Project entry reached this way still hands its approach to the scene, which draws the affordance.

## Every entry is a real `<button>`

A destination is an action inside this page, not a document to navigate to. A `<button>` is focusable, activated by both Enter and Space, and announced as a button without an attribute saying so; nothing sets `tabIndex`, so the tab order is the document order, which is the model's order. Each button hands its entity ID to a door in `activate.ts` (2.9): a Client button to `activateClient`, a Project button to `activateProject` with its own Client's ID. `overview` calls `pullBack`. The return is not in the index: since 3.8 `↩ resume the journey` is the corner chrome's slot, which calls `returnToRail` (below). The scene's Star and Planet clicks call the same doors, so the two surfaces cannot disagree about what activating a destination means.

`aria-pressed` on the Project buttons carries Focus, and only Focus. It is allowed where `aria-label` is banned because it is a different kind of attribute: it adds state and replaces nothing, so the announced name is still the title plus Deep/Shallow with "pressed" alongside it. The ARIA ban in `index-model.test.ts` is therefore the name-replacing family — `aria-label`, `aria-labelledby`, `aria-describedby` — and a case there proves the original `aria-label={project.depth}` regression still fails.

## One authority on where the visitor is

`state.ts` owns navigation state; the camera and the DOM index are both consumers and neither owns position (AD-9). Building the camera first and letting the canvas hold the current destination produces the inverted architecture AD-4 exists to forbid — one where the index translates render state rather than commanding it — so the authority lands before its second consumer exists, and the index subscribes to it today.

An authority with no subscriber is unfalsifiable, which is why the index is wired now rather than in 2.7. Selection sets state. Focus now has a second and third consumer — the panel and the camera's Focus move (2.7) — while `railPosition` has no consumer and, since 2.9, no caller: the Rail rig reads `scrollProgress`, and a Client button flies (`activateClient` → `enterFreeFlight`) rather than selecting a stop. `selectClient` stays exported and audited, unwired — recorded in `deferred-work.md`.

### One writer per field

**The one-writer table lives in the `state.ts` module header, and that is the only copy.** It is the one a test pins — `state.test.ts` asserts a row exists there for every field the store actually holds — so a second copy here would be a table nobody checks, and the two would disagree on wording and ordering within a story. A test also asserts this file has not grown its own rows back.

Continuous `scrollProgress` and discrete `railPosition` are separate fields with separate writers, and **no event writes two writers' fields**. Collapsing them would make "the Rail is between two Clients" and "the Rail stops at this Client" the same statement, and the two writers would fight over it every frame. If the discrete stop should ever follow scroll progress, that is `selectClient` called too — two named transitions rather than one event quietly writing both. Today it does not: scroll never selects a Client.

`focusOrigin` is stored at Focus entry and read at release (AD-16). Inferring it at release would answer a question about the past with the present, which is right until the first time `mode` has moved in between.

State changes **only through the named events** exported from `state.ts`. A `setState` in a renderer would be a transition nobody can find, nobody tested, and nothing stops from writing two writers' fields at once — see the tree-wide scan below.

### Who writes `scrollProgress`

Two callers of `advanceScroll`, and no third: the scroll input's handlers in `scene-host.tsx` (the wheel and the arrow keys, whose pure rules are `rail-input.ts`'s) and the `goHome` door in `activate.ts`, which the `Home` key calls to return to the opening frame. A wheel over the scene — and only over the scene: the listener sits on the `<div>` wrapping the scene boundary, so a wheel over the index scrolls the page normally — asks `wheelIntent(...)` and, only when the answer is not `null`, prevents the default and, on the Rail, calls `advanceScroll(next)`. A pinch-zoom (ctrl+wheel) and a horizontal-only wheel are therefore left to the browser. The listener is registered by hand with `{ passive: false }` because React attaches `wheel` passively, and a passive listener cannot stop the page scrolling under the camera. Progress is measured in stops: 0 is the opening frame and `k` the `k`-th Client stop, present first. The camera rig reads it and writes nothing back, and scrolling never calls `selectClient`, which stays `railPosition`'s one writer — with no caller since 2.9. The store itself stays unclamped; the range is `rail-input.ts`'s to enforce.

### Free flight, and the keyboard (2.9)

`flightTarget` is what free flight frames: a Client's stop, or `null` for the whole universe. `enterFreeFlight(target)` writes it with `mode` as one transition, and `enterRail()` writes `mode` alone — flight never writes `scrollProgress` or `railPosition`, so returning lands on the Rail exactly where it was left, and the camera eases back to the Rail's live pose (`src/render-scene/flight-model.ts`). In free flight with nothing focused the wheel over the scene is swallowed (`{ inert: true }`: prevented, nothing written). The keyboard is bound on `window`, so it works wherever DOM focus is: ↑/↓ step to the previous/next whole stop on the Rail and are swallowed in free flight; `Home` returns to the Rail's opening frame from either mode through the `goHome` door (`enterRail()` then `advanceScroll(0)`); while a Project is focused, or with a modifier held, no key is the Rail's and the panel scrolls natively. Until the scene has mounted (3.15) — the chunk still loading, or the boundary holding the index alone — neither the wheel nor ↑/↓/Home is the Rail's either: both rules answer `null`, nothing is prevented, and the page scrolls natively; `Escape` and the wheel's panel answer still work, because they are not Rail input. A key another handler already prevented, or one inside an IME composition, is left alone. A Client or `overview` activated while a Project is focused releases Focus first, then flies: a new destination is explicit navigation, and DOM focus stays on the door taken. Since 2.10 the return releases Focus first too; so does the Home door, defensively — Home while Focused is still the panel's, and never reaches it from the keyboard. Leaving free flight turns the corner slot's `↩ resume the journey` button back into the Rail's instruction text, so a ref cleanup on the button hands DOM focus to the index's `overview` (found by `OVERVIEW_ID`) when the button held it. Tab and Enter reach every Client and Project through the index's buttons, which call the same doors as a pointer. The handler never reads the event's target.

### Scroll has two meanings, chosen by state alone (2.7)

With a Project focused, the same wheel over the scene scrolls the panel instead: `wheelIntent` answers `{ panel: pixels }`, the handler prevents the default and calls `scrollBy` on the element named `FOCUS_PANEL_ID`, and `scrollProgress` is not written — so reading never moves the camera. The meaning comes from `focusedProjectId` and nothing else; the handler never reads the event's target and never hit-tests, and a scan in `rail-input.test.ts` fails if it starts to. A wheel over the panel itself never reaches the scene's listener: the panel is its own scroll container (`overflow-y: auto`, `overscroll-behavior: contain`) and scrolls natively.

## The Focus panel sits beside the scene, never over it (2.7)

Focus is one combined move: the camera eases to a pose that puts the Project off-centre in the half the panel leaves free (`src/render-scene/focus-model.ts`), and the panel slides in over the same `FOCUS_SECONDS` on the same curve (`focus-motion.ts`: CSS for the panel, the same control points solved in JS for the camera). Release is the same move reversed, and a release while the panel is still sliding in is shortened on both halves: the browser shortens the panel's reversed slide by the reversing shortening factor, and the camera's ease applies the same factor, so the two still end together. The canvas keeps its full width; the panel is `position: fixed` on the right at `min(560px, 46vw)`, and there is no scrim, dim, backdrop or modal (UX-DR20).

Focus is entered deliberately — the index `<button>` or a Planet click — and released by the panel's `release` button or the corner slot's `esc — release` (3.8). Hover reveals and never activates: since 3.4 a Planet hovered, or a Project button reached by keyboard, only draws that Project's affordance (`src/render-scene/affordance-model.ts`). DOM focus follows `focusMove`: on entry to the panel container (`tabindex="-1"`, labelled by its `<h2>`), on release back to the released Project's own index entry, found by `indexEntryId` (UX-DR40) — whichever door Focus came through. A release that travels is the exception: a Client, `overview` or a Star releases Focus and changes the flight key in the same render, and DOM focus stays on the door the visitor took rather than being pulled back to the entry. Closed, the panel is `visibility: hidden` once the slide ends — the reversed, shorter slide when a release interrupts the opening one (3.15, `panelSlide`) — so it leaves the tab order and the accessibility tree without a `transitionend` listener. `Escape` releases it too (2.10, below). The panel's typography is 3.6's and its reading position 3.7's (`focus-panel.css`).

**A → B cross-fades (2.8).** Moving Focus between Projects leaves the panel open, so its content changes in place: `crossFade` names the outgoing Project for `A → B` only, its blocks render once more in a layer over the incoming ones, and a layout effect — before the first paint of the swap — fades the incoming layer 0 → 1 and the outgoing one → 0 with WAAPI over `FOCUS_SECONDS` on `focusEasingCss()` — the duration the camera moves and the Motes condense in, so the three surfaces are one transition. The outgoing layer is `aria-hidden` and `inert` and its title carries no `id`, so the label, the accessibility tree and the tab order see only the incoming Project; DOM focus moves exactly as in 2.7. The leaving ID is held in a ref, written only on a render where the store's ID differs from the one the focus effect last recorded: repeated renders agree, and a re-render after the effect commits cannot unmount A mid-fade. `leavingAfter` keeps the layer through a release, so releasing during an `A → B` fade lets A finish fading as the panel slides out instead of cutting it. The layer is scrolled to where the reader was in A (tracked by a passive `scroll` listener, since after the swap the browser may clamp the position to B's length) before the panel returns to its top for B.

### The Skills are a list in the panel (3.5)

Between the field table and `release`, the panel carries the Project's Skills as a static `<ul aria-label="Skills">` in authored order, deduplicated — no visible heading, no live region, never a field-table row. The Motes' canvas labels are capped and may be hidden; this list is where every Skill is read.

## Escape releases one layer (2.10)

`Escape` is a door: `keyIntent` answers `{ release: true }` while a Project is focused or in free flight, and the `keydown` handler calls `releaseLayer()`. It releases the innermost layer and only that one — Focus if a Project is focused (the camera returns to the layer beneath, and DOM focus to the Project's entry), otherwise free flight back to the Rail where it was left (DOM focus to `overview` if the corner slot's button held it). On the Rail with nothing focused it is `null`: not prevented, nothing written. A modifier held (Shift+Esc included) is asked first and leaves the key alone, as does an IME composition or a key another handler took. A held `Escape`'s auto-repeats are left alone too, so one physical press releases one layer. So a second `Escape` after a Focus in flight returns to the Rail, and a third does nothing.

Every door that changes `mode` releases Focus first — a Client, `overview`, the return, and Home (defensively: the key is the panel's while focused, so only a direct caller can reach the door then) — so while a Project is focused `mode === focusOrigin`, executed over every sequence of up to four doors. That is what lets a Focus release return to the layer recorded at entry (AD-16) without writing `mode`.

## Reduced motion is one pace (2.10)

`prefers-reduced-motion: reduce` does not cut: every move still runs, continuously, from the pose drawn to its goal, in `duration × pace` (`REDUCED_MOTION_PACE`, 0.25). The camera's models advance their elapsed time by `clamp(dt) / pace` (flight, Focus, Condensation), the Rail spring's time constant is `RAIL_SPRING_SECONDS × pace`, and the panel's slide, its visibility delay and the cross-fade run on `FOCUS_SECONDS × pace` — each a ratio of elapsed time to duration, so the camera and the CSS stay in step. The Mote orbit clock alone stops (WCAG 2.3.3, Animation from Interactions). That is not WCAG 2.2.2 (Pause, Stop, Hide), which needs a control for everyone: at full motion the orbits still spin with no pause, and that stays open in `deferred-work.md`. Dwell and every rest pose are untouched. A running CSS transition keeps the duration it started with, so toggling the preference mid-slide desyncs one move by a few frames; that is accepted.

The preference lives in `motion-preference.ts`, a module-level value rather than a second store, written by one `matchMedia` listener in `scene-host.tsx` and read only by the rig, the Mote field, the panel and the corner chrome. An audit in `src/render-scene/scene-model.test.ts` pins that set, so no capability judgement can read it.

### A render loop reads with `getState()`, never with a hook

A camera subscribed reactively would re-render its whole tree on every progress write, sixty times a second, to obtain a value it is about to read anyway. So a frame callback calls `navigationStore.getState()` and takes the current value without subscribing. React consumers do the opposite — `useStore(navigationStore, selector)`, a selector and never the whole store, so a Client selection does not re-render every Project. `src/render-scene/rail-camera.tsx` is that loop; `state.ts` is what makes the path available.

### Why the store is pure `.ts` rather than a `create()` hook

`zustand`'s default `create` pulls React into the module graph, which would push the store's AC-bearing rules — exclusivity, writer separation, origin-at-entry — back onto source scans, the residual risk the model/renderer split below accepts. `createStore` from `zustand/vanilla` has no React import, and `zustand/react`'s `useStore(api, selector)` accepts exactly that store, so a pure store plus a React subscription is the supported shape rather than a workaround. Every rule the store obeys is therefore executed by `state.test.ts` rather than read off source.

### Malformed input fails loudly, for every writer

An unknown ID **throws** rather than no-ops. The store cannot validate membership — `src/shell/` may not import `src/derive/`, and no artifact is passed in — so validation is the caller's; what the store guarantees is that a malformed handle fails loudly naming the field and the value, rather than parking the visitor at a destination that does not exist. Same posture as `startsAt` in the derive layer.

The guarantee has to hold for *every* writer or it holds for none. Two ways it did not, both closed:

- **A padded ID is stored trimmed.** The guard validated `id.trim()` and then stored the raw `id`, so `'  client-zulu  '` passed the check and was parked as a string matching no artifact ID — a destination that does not exist, reached through the guard written to prevent exactly that. The value checked and the value kept are now one string.
- **`advanceScroll` rejects a non-finite value.** `NaN` is what arithmetic on an undefined scroll offset produces, and it propagates in silence: every comparison against it is false, so a camera reading it places the visitor nowhere and reports nothing. A store that threw on `''` while accepting `NaN` made its own claim true of one writer and false of the other.

Progress stays **unclamped in the store**: the store knows nothing of the Rail's length, so the range is enforced by its callers: `rail-input.ts`'s rules clamp to `[0, N]`, and `goHome` writes `0`. The store's guard checks that the value is a number, not what it means.

### The named-event contract is scanned for the tree, not for one file

`zustand` puts `setState` on the store object, so the type cannot forbid a consumer calling it; the contract that none does is held by a source scan — and that scan walks **every shipped file under `src/`**, exempting `state.ts` by name. A scan of one hard-coded file left `App.tsx`, a future `entry.ts` and `render-scene/` — which `src/render-scene/README.md:5` already declares imports this store — free to write two writers' fields in one statement, which is the precise thing the rule exists to prevent. The audit is a pure function over files, so it is driven over fixtures as well as over the real tree: a checker only ever run against a clean tree proves nothing about what it would reject.

What the scan reaches, and what it does not, is worth stating because the gap is permanent rather than a to-do. It catches a call (`store.setState(…)`), a bracket access (`store['setState']`) and a destructured alias (`const { setState: write } = store`); a computed key — `store['set' + 'State']` — defeats it, and no scan over text can close that. Comments and string literals are blanked before matching, in all three shapes prose takes, so these module headers can discuss `setState` at length without the audit firing on them. The contract is therefore enforced at the cost of having to write a violation deliberately, which is the honest claim; a stronger one would stop anyone checking.

## The corner chrome (3.8)

Exactly two lines, in opposite corners, 40px in (`--space-xl`), in the `chrome` type role at `ink-label` (DESIGN.md §7.9, UX-DR27). Top-left, `THOMAS NAVARRO · the model` — text, never a control; the Colophon route is 5.1's. Bottom-right, one stateful slot whose content comes from `mode` and `focusedProjectId` alone (`chromeSlot`): `scroll ↓ — time runs backward` on the Rail (text, not focusable), `↩ resume the journey` in free flight (a `<button>` → `returnToRail()`), and `esc — release` whenever a Project is focused, in either mode (a `<button>` → `releaseLayer()`). Each button's accessible name is its visible text. The strings are set as authored, with no `text-transform`: the ratified strings are mixed case, and the AC wins over DESIGN.md's capitals rule.

The return button lives here and only here (ruled 2a), so there is one return button; `Home` and `Escape` remain the keyboard's ways back to the Rail. While Focused the slot sits 40px left of the panel and moves with its slide (`slotStyle`: `right` over `FOCUS_SECONDS × pace` on the Focus curve). The chrome sits below the panel's layer, and its lines take no pointer; only the slot's button does. In `App.tsx` the document order is index, chrome, scene host, panel.

The slot is one persistent element in every state: only its content swaps (the instruction text, or the one button), so its `right` transition runs on every change of Focus — Rail ↔ Focus included — and it never mounts afresh at its final position.

DOM focus: when the slot's button unmounts while holding focus after a resume — by click, `Escape`, or `Home` (`goHome`) — a stable ref cleanup hands it to `overview`. The cleanup reads the button's last action off its own `data-action`, and does nothing after a release: a release from the Rail also unmounts the button, but its focus target is `focusMove`'s alone (the Project's entry), so focus moves once and never to `overview` first. A release in free flight keeps the same `<button>` element (release → resume), so the cleanup does not run there.

## The index precedes the camera

`src/App.tsx` renders the index synchronously from the statically imported artifact, so it is in the document at First Paint, before any 3D chunk has been asked for. This is AD-4 and it is the ordering, not a detail: building the camera first produces an architecture where the canvas is the real interface and the accessible surface is a translation of it, and the inversion stays invisible until assistive technology meets it.

Nothing here reads camera state, viewport size, or canvas hit-testing, so the index's structure, order and focusability are invariant under re-render and resize by construction rather than by care.
